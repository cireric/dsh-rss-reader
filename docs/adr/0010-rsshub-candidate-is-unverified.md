# ADR-0010：RSSHub 候选是「未验证」的——不预先抓一遍

- 状态：已采纳（2026-11-23）
- 适用：`discoverCandidates` 的 Radar 支路、`FeedCandidate.source === 'rsshub'` 的候选、R8b 的「不探测哪条路由真能取到」

## 背景

R8a 要在现有「粘贴网页 → 列出可订阅源」里补上 RSSHub Radar 这一路。现有那一路的做法是**逐个候选抓一遍**（`checkCandidate` → `parseFeed`），通过的才进列表、失败的带原因进警告。于是很自然地问：Radar 候选要不要也这样？

实测（2026-11-23，`rsshub.rssforever.com`）给了相反的答案：

- `/github/branches/DIYgod/RSSHub` → 200，**3.5s**；`/github/contributors/…` → 200，1.8s。
- `/bilibili/user/dynamic/208259` → **503**，1.4s。

RSSHub 的「取回」是一次**实时抓原始站点**，不是读静态文件：慢的几秒、被反爬的直接 503。这意味着：

1. 每个候选多 1–4 秒，一次发现最多 5 个候选 ⇒ 用户等十几秒；
2. **PLAN 点名的验收样本（B 站空间页）会因此判失败**——它的路由本来就被反爬挡住；
3. 「RSSHub 取不到」和「这个地址是错的」是两件事，前者随时间变化（实例限流、站点改版），在发现时刻抓一次并不能证明什么。

## 决定

1. Radar 候选**不做取回校验**，直接进候选列表，界面标 `RSSHub · 未验证`。
2. 校验只发生在用户点「添加」时，走现有 `addFeed`（那里本来就会抓一遍并给出失败原因）。
3. 界面文案不暗示「已验证」；`FeedCandidate.format` / `itemCount` 对这类候选缺省。
4. R8b 沿用同一条：路由探索只展示规则声明，不做「哪条能取到」的探测。

## 后果

- 用户可能添加一个当场取不到的订阅源——失败会出现在刷新日志与源状态里，可删可改，不是数据损坏。
- 发现保持「一次页面抓取 + 一次规则查询（~1KB）」的响应量级，与现有发现同一个数量级。
- 这条判据是**产品语义**，不是性能妥协：发现回答的是「这个网址能变成哪些订阅地址」，不是「这些地址现在能不能取到」。后者只有取一次才知道，且随时会变。
- 反悔成本低（加一次 `checkCandidate` 即可），但反悔会同时打破上面 1–3 三条，所以记在这里，避免后人把它当成遗漏。
