# ADR-0006：未读账目跟着显示窗走

- 状态：已采纳（2026-11-19）
- 适用：`src/endpoints.ts` 的 `carriesAccount` 合并、`src/unread.ts` 的账目、`src/client/account-mirror.ts` 与 5 个带账端点

## 背景

显示窗（今天 / 近 3 天 / 近 7 天，见 [ADR-0005](0005-display-window-is-published-at.md)）要同时作用于列表与未读计数。
但「未读账」不是只由 `overview` 产出：分发器会把 `accountOf(target)` 的**全量**账合并进每一个带账写端点的回包
（`markRead` / `unmarkRead` / `cleanup` / `toggleKeepUnread` / `toggleStar`，共 5 个），客户端 `applyAccount`
是**整份覆盖**。于是最省事的做法（只在 `overview` 上按窗统计）会有一个可见后果：
**标一条已读，窗口计数被写端点的全量账打回去**——用户看到「今天 3 条未读」在标读后仍然是 3。

三条路：①账目保持全量、窗内计数只作显示投影（便宜，但标读后滞后，且客户端要自己判窗口归属 = 第二份判据）；
②窗随账走（本 ADR）；③范围只影响列表、不做窗内未读计数（功能砍一半）。

## 决定

1. **显示窗随每个带账请求传递**：5 个 `carriesAccount` 端点的 payload 增加可选的 `from` / `to`（与 `overview` 同一形状）。
2. 分发器合并账目时按窗计算；**不传窗口 = 全量**（缺省不变，旧行为原样）。
3. 客户端只在 `accountMirror` 一处把当前窗口带上——5 个带账调用都走它，不在每个动作里各写一遍。
4. 不变量从「各源之和 = 总数」改成**「对同一个窗口：各源之和 = 总数」**。两个面板用不同窗口时，
   同一份数据会给出不同的未读数——这是正确的（各自描述自己的视野），但排障时要知道。
5. 范围版 `unreadPerFeed` 与全量版必须是**同一条 SQL 语义的两种参数**，并在同一夹具上逐键对账
   （与「未读判据」既有的对账纪律一致）。

## 后果

- `toggleStar` / `cleanup` 这类写端点会带一个与它们**写入对象无关**的日期范围。这不是耦合错误：
  回包里的账属于**调用方的视野**，客户端拿到它就是要覆盖显示。
- **新增带账端点必须声明并传递窗口**，否则它回全量账、客户端一覆盖就把角标打回全量。这是本 ADR 存在的主要理由。
- 显示窗的选择本身**不落盘**（每次打开回到「全部」），所以账目窗口不需要跨会话记忆。
- 若将来要做「两个窗口并存」（例如侧栏看今天、主列表看全部），账目也得跟着变成按视野分开——
  那是重开这个裁决，不是加一个字段。
