# ADR-0009：作者是 feed 给的原始字段——不推断、迁移不回填、已有值不覆盖

- 状态：已采纳（2026-11-22）
- 适用：`items.author`、`ItemRecord.author`、`ItemView.author`、`rss_search` / `rss_read_article` 的输出

## 背景

RSS 2.0 的 `dc:creator`（优先）与 `<author>`、RSS 1.0 的 `dc:creator`、Atom 的 `author.name` 都可能在条目上带作者。R12 要把它从解析层带到界面与搜索。三个问题必须一起回答：

1. **旧条目怎么办？** 迁移里回填需要重抓全部源（网络成本、改写历史），或从缓存的 `summary` 里猜（不可靠）。
2. **feed 改了作者名怎么办？** 跟随改名会改写历史条目的归属，与已读态/标签所指向的那条记录不再一致。
3. **缺失时怎么办？** 显示「未知作者」是编造；不显示才是诚实的降级。

这三个问题看似可以各自决定，实际上共享同一个前提：**作者是发布者给的原始元数据，不是我们从内容里推断出来的身份**。一旦承认这一点，「迁移回填」「跟随改名」就不再是「更完整的实现」，而是把原始记录改写成另一种东西。

## 决定

1. `author` 只来自解析层拿到的原值；`trim()` 后为空即 `undefined`。不剥邮箱、不拆「姓 名」、不统一大小写、不从正文/域名/头像推断。
2. **迁移不回填**：`v4→v5` 只 `ADD COLUMN`，升级瞬间旧行保持 NULL。
3. **刷新会做机会式补全**：某条目在库里没有作者、而这次响应给了作者 ⇒ 补上。范围永远是**本次响应里仍在的条目**（源回 304 时一条都不写；早已滚出源窗口的老条目保持空）。没有额外网络、没有重抓历史——它只接住 feed 这一次已经给出的值。
4. **已有作者不覆盖**：只有「原记录没有、这次解析有」才补；feed 改名不改写历史条目。
5. **界面只在有值时显示作者**；无值时不显示任何占位文案。作者名在行内单行省略，`title` 给全文；数据层不截断。
6. 搜索按作者原值做子串匹配（读路径与存储读侧共用同一个归一化函数），不做别名/同名合并。

## 后果

- **升级瞬间**所有旧条目都没有作者。此后各源只要返回完整正文，仍在响应里的老条目会陆续补上；从不再出现在响应里的条目保持空。用户看到的是「不显示」，不是「显示错」。
- 首轮刷新可能为「响应里仍在的老条目」各写一次 `updateItem`（一次性成本，随各源返回正文分批发生）；量在真机升级后按日志记录。
- feed 改名后，旧条目保留旧名、新条目用新名；同一作者在历史里可能有两个名字。这是有意为之：历史记录保持当时的归属。
- 作者不参与排序、不改变已读/星标/标签/进度；它只是一条元数据。

## 已知边界

- **Atom 的 feed 级 `<author>` 不回落**：解析只读 `entry.author[0].name`。只在 `<feed>` 上声明作者的源（Jekyll 一类生成器）本期所有条目无作者。Atom 规范允许 feed 级 author 作为条目默认署名，但那是「全源同一个署名」，对「区分同一个源里的不同作者」零增益，还可能给多作者博客一个不符的署名——要做单独立项。
- 作者名不做任何清洗之外的规范化（大小写、邮箱、姓/名拆分），因此同一作者在不同源/不同写法下不会被合并。

## 被拒绝的替代方案

- **迁移回填**（重抓全部源 / 从 `summary` 猜）：网络成本高，且猜出来的作者会制造「张冠李戴」；这与 `src/feed/date.ts` 的「不编造日期」是同一条纪律。
- **跟随 feed 改名**：会把历史条目改写成另一个人的作品，且与用户的已读态/标签历史不一致。
- **推断作者**（从邮箱、域名、正文猜）：不可靠，且错误无法被用户识别。
- **Atom feed 级作者回落**：见「已知边界」。
