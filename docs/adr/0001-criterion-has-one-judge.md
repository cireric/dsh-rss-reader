# ADR-0001：判据只有一个裁决者

- 状态：已采纳（2026-11-14）
- 适用：`retention.ts` / `store-sqlite.ts` 的清理判据；同样适用于 `isUnread` 一类「一份规则两种写法」的地方

## 背景

清理判据曾有两份实现：`retention.ts` 的 `selectCleanup`（自称口径之家）与 `SELECT_CLEANUP_IDS` 那条 SQL。
端点在拿到候选后「复跑」一次判据，看着像双保险。实际是**空操作**：三个适配器都在内部预筛，
候选集恒等于判定集；而自持实现回填候选行时把 `read / starred / kept` 写死成 `true / false / false`——
SQL 一旦放宽，判据看到的仍是「已读、未星标、未保持」，照样放行。

2026-11-14 的隔离实验实测：把 `kept_unread = 0` 放宽成 `>= 0` 后，一条 `kept_unread = 1` 的旧条目
进入候选、被列进删除集；纯函数用例一条都不会红。

## 决定

1. **判据的裁决者是 `selectCleanup`**，保护条款（星标、保持未读）只写在它里面。
2. SQL 只做**成本筛选**（`read_at IS NOT NULL AND recency < ?`），不替判据决定保护。
3. 适配器契约从「候选 = 判定集」改成 `候选 ⊇ 判定集`；候选行的判据字段**照列读**，不许回填。
4. 判据字段的等价由**行为断言**钉住（候选必须含受保护的行、删除集不许含它们），不用 SQL 文本断言。

## 后果

- 少取（SQL 比判据更窄）会变成「永远清不掉」——由对账用例守住，失败形态是**不删**而不是多删。
- 多取（连受保护的行一起捞）是正常的，判据会挡回去。
- SQL 里的任何宽容度变化都不再是行为变化，因此按「等价变异不入门槛」处理，不再为谓词本身设变异。
